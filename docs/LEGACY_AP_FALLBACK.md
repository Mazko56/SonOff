# Legacy Sonoff AP fallback (v1.5.0)

## Фактичний статус

Реалізовано **реальний Android-клієнт для історичного механізму Sonoff S31/частини старіших моделей**: пошук SSID `ITEAD-*`, підключення до конкретної Wi-Fi-мережі через **Android WifiNetworkSpecifier з системним підтвердженням**, перевірка AP-підмережі `10.10.7.0/24`, **GET `http://10.10.7.1/device` саме через Network.openConnection**, валідація `deviceid`/`apikey`, перевірка збігу повного ID зі SSID, збереження ключа в Android Keystore, повернення до LAN-пошуку.

Це НЕ доведене спарювання S60TPF. Деякі S60TPF можуть взагалі не мати такого AP і /device. Саме натискання кнопки не підключає пристрій автоматично до домашнього Wi-Fi. `GET /device` дозволяє лише спробувати прочитати доступні дані старого AP.

## Сценарій на пристрої

1. Встановити новий APK. Дозволити **Nearby Wi-Fi devices** і **Location** для Android-сканування; на деяких телефонах слід увімкнути системну «Геолокацію» (сканування Wi-Fi її потребує).
2. Звичайний LAN-пошук відбувається автоматично й не залежить від AP-шляху.
3. За наявності **власної, тестової** розетки з підтримкою ITEAD SoftAP перевести її у рекомендований виробником режим сумісного спарювання. **Цей крок може розірвати вже налаштоване з'єднання; не робіть його на робочій розетці без плану відновлення.**
4. Натиснути в існуючому інтерфейсі **«Шукати»**. Нових кнопок чи пояснювальних блоків немає. Система Android сама може показати діалог підтвердження підключення до `ITEAD-...`. На Android 10+ без цього підтвердження автоматично перемкнути мережу неможливо.
5. Додаток **не вводить Wi-Fi пароль домашньої мережі, не виконує перезавантаження, скидання, OTA чи перемикання реле**. Він лише читає `GET /device` і, якщо отримано сумісну відповідь, зберігає ключ. Потім потрібно забезпечити звичайне домашнє LAN-підключення розетки, після чого AES-зв'язок має окремо підтвердитися реальними зашифрованими даними.

## Діагностика

- `AP.SCAN.START` — запуск штатного сканування Wi-Fi.
- `AP.SCAN.NONE` — у свіжих Wi-Fi результатах немає SSID `ITEAD-...`. Це нормально для вже налаштованої розетки без AP.
- `AP.SCAN.OTHER` — помічені `SONOFF_*` точки, але їх не можна вважати сумісними із застарілим `/device` (наприклад, Matter/OpenEdge).
- `AP.PERMISSION.MISSING` / `.DENIED` — системні дозволи або Location недоступні.
- `AP.SCAN.MULTIPLE` — кілька AP-кандидатів; автоматичний вибір заблоковано.
- `AP.CONNECT.REQUEST` / `.AVAILABLE` / `.UNAVAILABLE` — Android OS підтвердила або не підтвердила локальний Wi-Fi шлях.
- `AP.PROBE.HTTP` — реальний код HTTP для `/device` у мережі AP.
- `AP.PROBE.ROOT` — резервний GET `/` тільки для перевірки доступності, **тіло відповіді не зчитується**.
- `AP.PROBE.FIELDS` — надійшли валідні `deviceid` і `apikey`, без розкриття секрету.
- `AP.PROBE.UNAVAILABLE` — API відсутній/несумісний/з'єднання не встановлено.
- `AP.KEY.STORED` — ключ зашифровано збережений у Keystore; **це ще не успішна авторизація на LAN**.
- `AP.RETURN.LAN` — звільнено тимчасову мережу AP, додаток повертається до сканування домашньої мережі.
- `LAN.READONLY.RESULT` і `ACCESS_KEY_REQUIRED` — зашифрована розетка відповіла, але відкритих даних немає; замість безкінечного «очікування» показано встановлений результат.
- `MDNS.DECRYPT.OK` / `LAN.REPLY.STATE` / `RELAY.CONFIRMED` — тільки вони підтверджують справжні доступ/дані/команду відповідно.

## Додаткові штатні маршрути (залишено з v1.4)

- NSD + mDNS, з резервним визначенням адреси із джерела пакета за відсутності A-record;
- локальний AES-LAN із раніше збереженим `devicekey`;
- відкритий DIY (`diy_plug`), читання `/zeroconf/info` і керування тільки після підтвердження стану;
- read-only `getState` → `info`, TCP/HTTP і перевірка 401 для зашифрованих пристроїв без ключа;
- альтернативи `switch` / `switches`, профілі AlexxIT + Urban82, розшифрування mDNS стану;
- пасивне виявлення Matter (без commissioning).

Жоден із цих шляхів не обходить шифрування S60TPF без належного ключа.

## Симулятори та перевірки

`py -m unittest discover -s tests -v` — **26** локальних лабораторних перевірок, включно з компіляцією частини Java з Android-заглушками та емуляторами шифрованого/DIY/API. Ці тести не означають повної Android SDK збірки, перевірки Android системного вибору Wi-Fi чи фізичної розетки.

`py tests\\fake_legacy_ap.py --host 127.0.0.1 --port 8092` — запускає **лише HTTP-макет** `/device`, не створює точку доступу. На ПК: `curl http://127.0.0.1:8092/device`. Він НЕ перевіряє роботу Android NetworkSpecifier і НЕ дає заводський `devicekey` S60TPF.
